# Issue #1280: No keyboard focus after dialog

This was a real issue and we implented the fix that is described at the end as workaround. The following text ist completely created by Copilot (and checked by me for correct informations regarding error and workaround, if the fix works this way you have to test yourself).

**Summary**
After executing an ICommand via a Ribbon button, Keyboard.FocusedElement is set to null. This breaks WPF's internal focus-restore mechanism when a ShowDialog() call follows — after closing the dialog, the main window no longer accepts keyboard input.
**Technical Root Cause**
The Ribbon control is its own WPF FocusScope (FocusManager.IsFocusScope="True"). When a Fluent:Button is clicked and its ICommand executes, it releases keyboard focus — but Fluent Ribbon does not explicitly restore focus to the last focused element outside the Ribbon's FocusScope.
WPF's ShowDialog() internally saves Keyboard.FocusedElement before opening the dialog (as restoreFocusElement) in order to restore it after closing. If that value is null, the restoration silently fails:

_// WPF internals (simplified):_
IInputElement restoreFocusElement = Keyboard.FocusedElement;  // → null after Ribbon click
dialog.ShowDialog();
restoreFocusElement?.Focus();  // → null?.Focus() → no effect

The result: IsKeyboardFocusWithin = false on the RibbonWindow, PreviewKeyDown no longer routes, and all keyboard input is "swallowed" until the user presses Tab or clicks a focusable element.
**Comparison with Standard WPF ToolBar**
WPF's built-in ToolBar solves this explicitly: after a button click, the ToolBar returns focus to the previously focused element in the main content area. Fluent Ribbon is missing this logic.

**Minimal Reproduction**
_// In a RibbonWindow, Ribbon button with this command handler:_
private void MyRibbonButton_Executed(object sender, ExecutedRoutedEventArgs e)
{
    // After this ShowDialog() returns → keyboard input no longer works
    new MyDialog { Owner = this }.ShowDialog();
}

**Steps:**
1.	Start the application
2.	Click a Ribbon button → dialog opens
3.	Close the dialog (Escape / Cancel)
4.	Press any key → no event fires, keyboard input is swallowed
5.	Press Tab or click a button → keyboard input works again
**Expected Behavior**
After a command is executed via a Ribbon button, Keyboard.FocusedElement should point to a valid element in the main content area (analogous to ToolBar behavior).
**Suggested Fix in Fluent Ribbon**
In the click/command execution pipeline of Ribbon buttons, after ICommand.Execute(...):

_// Restore focus to the last focused element outside the Ribbon FocusScope:_
Window parentWindow = Window.GetWindow(this);
if (parentWindow != null && !parentWindow.IsKeyboardFocusWithin)
{
    parentWindow.MoveFocus(new TraversalRequest(FocusNavigationDirection.First));
}

Alternatively, RibbonWindow could override OnActivated and ensure the same — however, that is an application-level workaround, not a fix for the underlying issue.

## mgrusigno commented on 2026-06-15T07:54:57Z

I know this is somewhat like Chinese whispers. But I let Copilot investigate further to get the correct root cause. But it seems this ticket should be routet to the ControlzEx development:

Thank you for the clarification — you are correct that Fluent.Ribbon itself does not set IsFocusScope since version 3, so the root cause is not there.

After further investigation we now believe the issue is caused by ControlzEx's WindowChrome implementation, specifically its HwndSource message hook handling of WM_ACTIVATE.

**Steps to reproduce:**
1.	Open a modal WPF dialog via ShowDialog() with a RibbonWindow as owner
2.	Close the dialog (e.g. via Cancel / Escape)
3.	Press any key → no keyboard input is processed
4.	Press Tab or click any focusable control → keyboard input works again

**Observed:** After the dialog closes, _IsKeyboardFocusWithin_ is false on the RibbonWindow. _OnPreviewKeyDown_ no longer fires.

**Root cause hypothesis:** WPF's own focus-restore path in _HwndSource.OnMessage_ relies on receiving _WM_ACTIVATE (WA_ACTIVE / WA_CLICKACTIVE)_ with _handled = false_ in order to execute its internal __restoreFocusMode_ logic and call _Keyboard.Focus_ on the previously focused element. ControlzEx registers its _HwndSource_ hook in the _RibbonWindow_ constructor (before _OnSourceInitialized_), and Windows processes hooks in LIFO order. If ControlzEx's hook marks _WM_ACTIVATE_ as handled before WPF's own _HwndSource_ dispatcher processes it, WPF's focus-restore never runs — leaving no element with keyboard focus.

Workaround on application level:

```
protected override void OnActivated(EventArgs e)
{
    base.OnActivated(e);
    if (!IsKeyboardFocusWithin)
        MoveFocus(new TraversalRequest(FocusNavigationDirection.First));
}
```
This works reliably, but it is a compensation for a missing focus-restore that should happen automatically. We would appreciate it if this could be confirmed or ruled out on the ControlzEx side.
