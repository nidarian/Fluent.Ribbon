# Issue #1267: Fluent ribbon startup time dominated by resource dictionary merging

- **State:** closed
- **Author:** ekalchev
- **Created:** 2026-02-13T08:03:51Z
- **Closed:** 2026-03-12T19:51:00Z
- **Labels:** Feature :1st_place_medal:
- **Original:** https://github.com/fluentribbon/Fluent.Ribbon/issues/1267

We are trying to improve our app startup time which uses Fluent ribbon. Our measurements shows that significant time is spent in loading the Fluent.Ribbon xaml dictionaries.

<img width="1062" height="82" alt="Image" src="https://github.com/user-attachments/assets/2938d02d-0fea-4f27-9b61-44d426cf3e0c" />

Profiling data indicates that Fluent.Ribbon's startup performance is significantly impacted by the loading of all theme color dictionaries. While WPF resource instantiation is technically lazy, the initial disk I/O and BAML parsing for large files—specifically styles.baml (approx. 16k lines)—create a measurable bottleneck.
On a high-end machine, we observe a hot-start time of 96ms, but this scales up to 500ms (5x) during a cold start due to page misses. On average user hardware, these times are roughly 3x higher.
This overhead is particularly redundant for applications that fully customize the Ribbon's appearance by redefining styles and templates. In these cases, we pay the performance penalty twice: first to load the default resources during initialization, and again to load our custom overrides.

**Suggestion:**
Introduce an "advanced scenario" switch to disable the automatic loading of default resource dictionaries. By allowing users to opt out of the default theme registration and provide their own resources exclusively, we can significantly reduce the cold-start footprint and enable much faster startup for performance-critical applications.

<img width="1381" height="1317" alt="Image" src="https://github.com/user-attachments/assets/f9d2a8ce-955a-4c73-ba42-e43bb85fac74" />

Additionally, if you want to further optimize resource utilization I can propose a solution found in Visual Studio source code, where each control resource is stored in its own unique resource dictionary and the xaml/baml is loaded on demand when the resource style key is requested. Here some source code.

```CSharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Text;
using System.Threading.Tasks;
using System.Windows;

namespace Wpf.Resources
{
    public class DeferredStyleResourceDictionary : ResourceDictionary
    {
        ....
        protected override void OnGettingValue(object key, ref object value, out bool canCache)
        {
            object RealizeValue(object key, string uriString)
            {
                Uri uri = new Uri(uriString, UriKind.RelativeOrAbsolute);
                ResourceDictionary resourceDictionary = new ResourceDictionary { Source = uri };
                object obj = resourceDictionary[key];
                realizedStyles.Add(key, obj);
                return obj;
            }

            if (realizedStyles.TryGetValue(key, out value))
            {
                canCache = true;
                return;
            }

            if (defaultStyles.TryGetValue(key, out string text))
            {
                value = RealizeValue(key, text);
                canCache = true;
                return;
            }

            base.OnGettingValue(key, ref value, out canCache);
        }
    }
}

```

```
The deferred content mechanism IS working — values are NOT being instantiated. But the bottleneck is not where you'd expect. Here's the breakdown:

  Where the 87ms goes

  87ms  set_Source
  ├── 80ms  BAML Loading (TransformNodes)
  │   ├── 49ms  SetKeys()                        ← 56% of total!
  │   │   └── 46ms  SetOptimizedStaticResources() ← THE BOTTLENECK
  │   │       └── 46ms  StaticResourceExtension.FindResourceInEnviroment()
  │   │           ├── 21ms  GetAllAmbientValues()
  │   │           │   └── 12ms  LOCK CONTENTION (kernel thread wait!)
  │   │           ├── 12ms  JIT_NewArr1 (array allocations)
  │   │           ├── 9ms   FindAmbientValues()
  │   │           ├── 5ms   GetMember() (XAML type metadata)
  │   │           └── 3.9ms Contains() (dictionary lookups)
  │   ├── 11ms  Baml2006Reader.Read() (reading BAML records)
  │   ├── 6.5ms SetDeferrableContent() (reading key table)
  │   └── 3ms   Hashtable.Insert
  └── 2.5ms  GetResponseStream (fetching the .baml from assembly)

  The real problem: OptimizedStaticResource resolution during key loading

  Even though values are deferred, the BAML key section contains OptimizedStaticResource entries. These are StaticResource references that appear within the key records. From the source code we saw earlier in
  SetKeys:

  for (int i = 0; i < keyCollection.Count; i++)
  {
      KeyRecord keyRecord = keyCollection[i];
      // ...
      if (keyRecord.HasStaticResources)
          SetOptimizedStaticResources(keyRecord.StaticResources, ...);  // ← 46ms HERE
      _baseDictionary.Add(value, keyRecord);
  }

  For every OptimizedStaticResource, SetOptimizedStaticResources calls StaticResourceExtension.TryProvideValueImpl() which tries to resolve the resource immediately by walking up the entire XAML ambient value
  chain. This is a full graph walk, not a simple dictionary lookup.

  Three compounding issues
  Cost: 12ms
  Cause: Lock contention — RtlpEnterCriticalSectionContended → NtWaitForAlertByThreadId. Another thread (likely JIT compiler) holds a CLR critical section, and your UI thread blocks waiting for it. This is pure

    thread scheduling overhead.
  ────────────────────────────────────────
  Cost: 12ms
  Cause: Array allocations — JIT_NewArr1 is called per-lookup inside GetAllAmbientValues. Each StaticResource resolution allocates arrays to collect ambient values. With hundreds of resources, this is heavy GC
    pressure.
  ────────────────────────────────────────
  Cost: 22ms
  Cause: Ambient value walking — FindAmbientValues + GetAllAmbientValues walk the XamlObjectWriter context stack frame by frame, checking each frame's ambient properties. Your ControlzEx theme dictionary likely

    has many cross-referencing resources (brushes referencing colors, styles referencing brushes, etc.), each triggering this walk.
  Why ControlzEx theme dictionaries are especially susceptible

  This is a ControlzEx/MahApps theme dictionary — these tend to have hundreds of resources with heavy StaticResource cross-references (e.g., SomeBrush references SomeColor, SomeStyle references SomeBrush,
  etc.). Each cross-reference inside the deferred key section triggers a full ambient resolution.

  What you can do about it

  1. Split the dictionary — Break the large theme dictionary into smaller MergedDictionaries. Resources referencing each other should live in the same sub-dictionary to reduce ambient walk depth.
  2. Replace StaticResource with DynamicResource where feasible — DynamicResource references are NOT resolved during SetKeys. They're deferred until the resource is actually used. This directly avoids the
  SetOptimizedStaticResources path.
  3. Move loading off the critical path — If this is happening at startup, load the theme dictionary earlier on a background thread (if the dictionary doesn't need to be attached to the visual tree
  immediately), or defer it past the first render.
  4. The 12ms lock contention is a JIT warmup artifact — if this is a cold-start measurement, it will be smaller on subsequent loads. Consider using ReadyToRun (R2R) compilation for the assembly containing the
  theme XAML to reduce JIT pressure.
```

Telerik WPF controls library approach doesn't use Generic.xaml and they require manually to merge their xaml files in your app resources in order to have styles for their controls. They have separate .dll file for each style/theme assembly. Having a nuget package for themes is overkill. You just ship all the theme assemblies in your main package and let the user choose from them. Probably you won't like this approach as this is shift from Generic.xaml and will introduce breaking change. 

Alternative approach for having a switch that will turn off default styles may be achieved with this

```CSharp
public class ConditionalLibraryStyles : ResourceDictionary
{
    public ConditionalLibraryStyles()
    {
        // static property/field. must be set before the Generic.xaml loading
        if(FluentRuntimeSwitches.DisableDefaultStyleLoading == false)
        {
            Source = new Uri("styles.xaml", UriKind.RelativeOrAbsolute) 
        }
    }
}
```
This will be Generic.xaml
```XML
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
                    xmlns:local="clr-namespace:YourLibraryNamespace">
    <ResourceDictionary.MergedDictionaries>
        <local:ConditionalLibraryStyles />
    </ResourceDictionary.MergedDictionaries>
</ResourceDictionary>
```

now let the users that use the switch to provide necessary default styles and colors.
